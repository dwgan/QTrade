# 防作弊回测与策略验证方案

## 1. 目标

本阶段的目标不是单纯增加一张资金曲线，而是建立一套可审计、可复现、能明确区分“研究结果”和“真实证据”的策略验证流程。

回测系统需要回答以下问题：

1. 每个交易日使用的信息，在当时是否真的已经公开并可获得？
2. 股票池是否包含当时仍在市场中的失败公司和退市公司？
3. 信号产生后，是否按照现实中可执行的时间和价格交易？
4. 策略规则是否在查看测试结果前就已经冻结？
5. 尝试失败的策略是否也被记录，而不是只保留表现最好的版本？
6. 策略在未参与开发的数据和未来新增数据上是否仍然有效？

只有同时满足这些条件，回测结果才可以作为操作参考。历史回测无法彻底消除研究者对历史行情的主观记忆，因此最终结论仍必须经过一段真正的前瞻模拟观察。

## 2. 当前实现评估

### 2.1 已有能力

当前项目已经具备以下正确基础：

- 使用归档后的候选股排名快照进行回测。
- T 日生成信号，最早在 T+1 执行。
- 对停牌、涨停无法买入、跌停无法卖出进行约束。
- 未成交订单可在后续交易日继续尝试。
- 支持手续费、滑点和成本敏感性分析。
- 支持样本内、样本外的结果拆分。
- 财务因子计算时使用 `ann_date <= as_of_date` 过滤公告。
- 输出收益率、波动率、夏普比率、最大回撤等基本指标。

### 2.2 不能作为严格证据的缺口

当前实现仍存在以下关键缺口：

- 样本外区间只是结果标签，没有真正封存；查看结果后仍可修改策略并再次使用同一区间。
- 同一日期的因子快照可能被重新生成和覆盖，缺少不可变版本、哈希和数据血缘。
- 缺少实验登记簿，无法知道总共尝试过多少策略和参数组合。
- 缺少历史时点股票池、指数成分、ST 状态、行业分类等有效期数据的完整审计。
- 缺少退市股票和历史成分股的系统性处理，可能产生幸存者偏差。
- 只有少量历史信号快照，样本量不足以验证策略。
- 回测仍是目标权重级模型，尚未完整模拟股数、100 股整数手、现金、最低佣金和成交容量。
- 当前主要按 T+1 收盘价成交，缺少开盘价、VWAP 和延迟成交的敏感性验证。
- 尚未实现滚动样本外验证、参数稳定性、年度分解和多重试验校正。

因此，当前模块应定义为“研究用回测原型”，升级完成后才定义为“可审计的策略验证系统”。

## 3. 必须防止的偏差

### 3.1 未来数据泄漏

在 T 日信号中使用 T 日之后才公开的财报、指数成分、行业变更或公司状态。

防范要求：

- 所有数据增加 `available_from` 字段，表示市场参与者最早可以使用该信息的交易日。
- 因子只能读取 `available_from <= signal_date` 的记录。
- 财报在公告日收盘后发布时，保守处理为下一交易日才可用。
- 测试中主动注入未来数据，验证系统必须拒绝使用。

### 3.2 幸存者偏差

使用今天仍上市的公司反推过去，遗漏后来退市、暂停上市或经营失败的公司。

防范要求：

- 股票池按历史日期重建。
- 保留退市证券的历史行情和状态。
- 指数策略使用当时生效的成分股，不能使用当前成分股。
- 历史回测不得通过当前证券主表的上市状态筛选过去样本。

### 3.3 修订数据偏差

使用后来修订过的财务数据替代市场当时看到的数据。

防范要求：

- 原始财务披露按公告版本保存。
- 同一报告期的更正公告作为新版本，不覆盖旧版本。
- 回测依据该日期当时最新可见的版本计算。
- 数据清单记录抓取时间、公告时间、版本和内容哈希。

### 3.4 执行价格偏差

使用产生信号所需的收盘价，同时假设自己按同一个收盘价完成交易。

防范要求：

- T 日收盘后生成的信号，基准执行模型使用 T+1 开盘价或 T+1 VWAP。
- T+1 收盘价只作为一种对照场景，不能是唯一结论。
- 无成交、停牌、一字板、涨跌停和流动性不足必须产生真实未成交。

### 3.5 数据窥探与策略过拟合

虽然代码没有直接读取未来字段，但研究者看过后期表现后不断修改规则，直到历史结果变好。这同样属于使用未来信息。

防范要求：

- 在运行验证集和封存测试集之前冻结策略协议。
- 记录所有成功和失败的参数试验。
- 查看封存测试结果后，只要修改策略，原测试集就视为已污染。
- 被污染的数据以后只能作为开发数据，不能继续充当独立证据。

## 4. 策略预注册协议

每一次正式验证必须先创建一份策略协议：

```text
research/protocols/<protocol_id>.yaml
```

协议至少包含：

- 研究假设和经济逻辑。
- 股票池及历史股票池生成规则。
- 因子公式、方向、去极值、标准化和缺失值规则。
- 因子权重，或事先限定的参数搜索网格。
- 调仓频率、持有数量和行业约束。
- 信号时点和允许使用的数据截止时点。
- 成交价格模型、费用、滑点和容量假设。
- 基准指数。
- 开发集、验证集和封存测试集日期。
- 主要指标、辅助指标和失败条件。
- 本次允许执行的参数试验数量。
- 数据版本、代码 Git 提交号和配置哈希。
- 创建时间、冻结时间和协议状态。

协议生命周期为：

```text
draft
  -> frozen
  -> development_completed
  -> validation_completed
  -> holdout_revealed
  -> shadow_observation
  -> accepted / rejected / retired
```

协议冻结后禁止原地修改。任何规则变化都必须：

1. 创建新的 `protocol_id`。
2. 记录修改原因和所依据的信息。
3. 关联父协议。
4. 将已经看过的验证或测试区间标记为“已污染”。

这样可以明确区分“原始假设得到验证”和“根据历史结果拟合出的新假设”。

## 5. 数据分区和封存规则

### 5.1 四层时间分区

建议首版采用以下逻辑，具体日期在第一次正式实验冻结前根据数据完整度确定：

| 分区 | 用途 | 是否允许反复查看 | 是否允许调参 |
| --- | --- | --- | --- |
| 开发集 | 构造因子、排错和初步选参 | 是 | 是 |
| 验证集 | 在有限候选中选择方案 | 有限 | 仅限协议声明的网格 |
| 封存测试集 | 对冻结策略进行一次性检验 | 揭晓前否 | 否 |
| 前瞻观察集 | 从冻结日起积累的新市场数据 | 按日查看 | 否 |

一个可供首轮讨论的日期方案为：

- 开发集：2015-01-01 至 2020-12-31。
- 验证集：2021-01-01 至 2022-12-31。
- 封存测试集：2023-01-01 至 2024-12-31。
- 前瞻观察集：策略正式冻结后的新增交易日。

日期不是固定真理。选择后必须写入协议并冻结，不能因为某个区间表现不好而移动边界。

### 5.2 对历史封存测试的诚实限制

即使程序在运行前隐藏 2023—2024 年的详细结果，研究者仍可能凭记忆知道这段时间的市场风格。因此：

- 历史封存测试能够减少直接调参，但不能完全排除主观历史认知。
- 历史测试通过只能得到“值得进入前瞻观察”的结论。
- 真正未见数据只能来自策略冻结之后的新交易日。
- 首版建议至少进行 3 个月前瞻模拟；更可靠的评价应覆盖 6—12 个月和多种市场环境。

## 6. 历史数据的时点一致性

### 6.1 数据记录规范

每类数据至少保留以下时间信息：

- `business_date`：数据描述的业务日期。
- `announced_at`：信息公开时间。
- `available_from`：策略允许使用的首个交易日。
- `fetched_at`：系统抓取时间。
- `source`：数据来源。
- `source_version`：来源版本或批次。
- `content_hash`：原始内容哈希。

### 6.2 必须按历史时点重建的数据

- 上市和退市状态。
- ST、风险警示、停复牌状态。
- 指数历史成分及生效区间。
- 行业分类及生效区间。
- 涨跌停规则和证券所属板块。
- 复权因子及公司行为。
- 财报公告、更正公告和可用日期。
- 日行情、成交额、换手率和每日估值指标。

### 6.3 数据质量闸门

正式回测前必须自动生成数据审计报告。出现以下情况时，回测应失败而不是静默继续：

- 存在 `available_from > signal_date` 的输入记录。
- 某个调仓日无法构造历史股票池。
- 基准或组合缺失关键交易日。
- 大量股票价格缺失且超过协议阈值。
- 数据内容哈希与冻结协议不一致。
- 同一数据版本出现未经声明的覆盖。

## 7. 历史信号重建

### 7.1 信号包

每个历史调仓日生成一个不可覆盖的信号包，包含：

- 信号日期。
- 候选股票、分数、排名和剔除原因。
- 每个因子的原始值和标准化值。
- 使用的数据分区及内容哈希。
- 策略协议 ID 和配置哈希。
- 代码 Git 提交号。
- 生成时间。
- `reconstructed` 或 `live_observed` 标志。

历史重建信号与项目每天真实运行时产生的信号必须分开保存，不能把事后重建文件伪装成当时已经存在的实盘信号。

### 7.2 批量生成规则

- 只能通过冻结协议批量生成，禁止在单个日期上手动修改参数。
- 因子计算程序只能访问当前信号日期允许的数据切片。
- 结果目录使用协议 ID、数据版本和运行 ID 隔离。
- 已完成运行不得覆盖；重跑产生新的运行 ID。
- 运行前后生成清单和哈希，用于复现和审计。

## 8. 回测执行模型升级

### 8.1 账户和订单

从目标权重模型升级为账户级模拟：

- 现金余额。
- 持仓股数。
- A 股 100 股整数手约束。
- 订单、部分成交、未成交和撤单。
- 卖出所得资金的可用规则。
- 停牌、涨跌停和退市处理。

### 8.2 费用

费用模型至少包括：

- 买卖佣金。
- 最低佣金。
- 卖出印花税。
- 过户费。
- 滑点。
- 市场冲击和成交容量限制。

所有费率必须带有效日期，避免用当前费率覆盖全部历史。

### 8.3 成交场景

至少同时运行：

1. T+1 开盘成交。
2. T+1 VWAP 或近似均价成交。
3. T+1 收盘成交。
4. 信号延迟一个额外交易日成交。
5. 基准成本、两倍成本和更严格容量约束。

只有在多种合理成交假设下方向一致，策略结论才较可信。

## 9. 验证方法

### 9.1 因子层

- Rank IC、IC 均值、ICIR。
- 分组收益和多空差。
- 分组单调性。
- 年度、牛熊阶段、大小市值和行业分解。
- 换手率、覆盖率和缺失率。
- 对 IC 和分组差使用自助法置信区间。
- 对时间序列相关性使用适当的稳健误差处理。

### 9.2 组合层

- 年化收益、年化超额收益。
- 波动率、夏普、Sortino、Calmar。
- 最大回撤及恢复时间。
- 月度和年度胜率。
- 相对基准回撤。
- 换手率和交易成本占比。
- 行业、个股和风格暴露。
- 收益对少数年份或少数股票的集中度。
- 容量估计和成交参与率。

### 9.3 稳健性

- 相邻参数是否保持同方向，而不是只有单一参数尖峰有效。
- 调仓日平移后结果是否稳定。
- 成交延迟后结果是否仍有意义。
- 成本加倍后是否仍保持正向超额。
- 不同市场阶段是否完全依赖单一行情。
- 滚动训练、随后测试的 walk-forward 结果。
- 与简单基线策略比较，而不仅与指数比较。

简单基线至少包括：

- 等权股票池。
- 低换手的市值或质量基线。
- 当前策略去掉某个因子后的消融版本。

### 9.4 多重试验

每次因子、权重、阈值或持股数变化都计为一次试验。报告必须展示：

- 总试验数。
- 成功和失败试验。
- 策略家族关系。
- 原始统计结果。
- 考虑多次尝试后的置信度。

第一版至少实现完整试验台账和 FDR 校正；后续可增加 Deflated Sharpe Ratio、White Reality Check 或 SPA 等方法。

## 10. 建议的首版通过条件

通过条件必须在测试集揭晓前冻结。以下为首版建议默认值，最终以协议为准：

### 10.1 数据合规

- 未来数据泄漏检测为 0 条。
- 历史股票池缺失调仓日为 0 个。
- 100% 信号包具备协议、代码和数据哈希。
- 任何超过协议阈值的数据缺失都使本次运行无效。

### 10.2 研究有效性

- 至少覆盖 5 年开发与验证数据。
- 至少包含 36 个独立调仓观察点；月度策略建议更多。
- 验证集因子方向与开发集一致。
- 参数邻域大部分结果方向一致，不存在明显单点尖峰。
- 结果不完全由单一年份或少数股票贡献。

### 10.3 组合有效性

- 验证集和封存测试集在基准成本后均取得正超额。
- 两倍成本或延迟成交场景下，策略方向不发生灾难性反转。
- 最大回撤和行业集中度不超过协议上限。
- 相比简单基线存在稳定改进。

若策略未通过，应明确标记为 `rejected` 或仅保留为研究假设，不能通过临时修改规则“救活”同一次实验。

## 11. 策略变更规则

查看结果后的修改分为三类：

### 11.1 实现缺陷修复

例如日期错位、费用计算错误或数据重复。允许修复，但必须：

- 记录缺陷和影响范围。
- 将原运行标记为无效。
- 创建新运行 ID。
- 从全部区间重新运行。

### 11.2 协议内参数选择

仅允许在预先声明的验证集和参数网格内进行。不能临时扩大参数范围。

### 11.3 策略逻辑变更

增加因子、改变过滤条件、修改权重或持股规则都属于新策略：

- 创建新协议版本。
- 旧验证数据转为已知信息。
- 需要新的未见测试数据，或重新进入前瞻观察。

## 12. 用户界面规划

新增“策略验证”页面，避免只展示漂亮的收益曲线。页面包括：

- 策略协议和当前生命周期状态。
- 数据版本、代码版本和防泄漏审计结果。
- 开发集、验证集、封存测试集和前瞻集边界。
- 封存测试是否已揭晓及揭晓时间。
- 资金曲线、超额曲线和回撤曲线。
- 年度/月度结果表。
- 因子 IC 和分组收益。
- 成本、成交延迟和参数邻域敏感性。
- 历次试验，包括失败版本。
- 系统结论：通过、拒绝、数据无效或继续观察。

界面不得默认只展示最优参数；必须优先展示冻结协议的主结果。

## 13. 实施顺序

### 阶段 A：研究协议和实验登记

- 增加协议数据模型、创建、冻结和版本化命令。
- 增加实验台账和策略生命周期。
- 保存 Git 提交号、配置哈希和数据版本。
- 禁止覆盖冻结协议和已归档运行。

验收标准：任意正式回测都能回答“谁、何时、用什么规则和什么数据运行”。

### 阶段 B：时点一致性数据层

- 补齐历史股票池、指数成分、ST、行业和退市信息。
- 为财务和分类数据增加 `available_from`。
- 建立原始数据清单和内容哈希。
- 实现未来数据、缺失数据和覆盖行为审计。

验收标准：自动测试故意放入一条未来记录时，正式回测必须失败。

### 阶段 C：不可变历史信号

- 按冻结协议批量生成历史调仓日信号。
- 保存信号输入血缘、排名详情和哈希。
- 区分重建信号与真实每日信号。
- 建立样本量和完整率报告。

验收标准：同一输入可完全复现；不同输入不得覆盖旧信号。

### 阶段 D：回测引擎 2.0

- 增加账户、股数、订单、整数手和完整费用模型。
- 增加开盘、VWAP、收盘、延迟和容量场景。
- 增加年度、月度、暴露、集中度和容量指标。
- 实现 walk-forward 和参数稳定性分析。

验收标准：所有成交都能追溯到信号、订单、价格和费用。

### 阶段 E：封存验证和报告

- 运行开发集和验证集。
- 冻结最终候选策略。
- 一次性运行封存测试集。
- 输出包括失败试验在内的完整研究报告。

验收标准：测试集揭晓后修改策略会自动创建新版本，并将原测试集标记为已知数据。

### 阶段 F：前瞻模拟观察

- 每日按冻结版本运行。
- 保存当天真实产生的信号，不允许补写为实时信号。
- 记录建议价格、次日可执行价格和实际后续表现。
- 至少观察 3 个月，再决定是否将其作为人工操作参考。

验收标准：前瞻结果和历史重建结果分别展示，不能混合。

## 14. 第一轮开发范围

为了先建立正确的研究纪律，下一轮代码优先实现：

1. 策略协议模型及 `draft/frozen` 状态。
2. 协议冻结后的不可修改和哈希校验。
3. 实验运行登记簿。
4. 数据集分区和封存测试集状态。
5. 回测报告写入协议 ID、代码提交号和数据版本。
6. 时间泄漏自动测试。

完成以上基础后，再批量回填长周期历史数据和升级成交引擎。这个顺序可以避免先产生大量无法证明来源、也无法判断是否被反复调参污染的回测结果。

### 15.1 创建草稿协议

以下日期仅为示例。第一次正式研究前应结合可用数据长度确定，并且不要在看过封存区间结果后调整：

```powershell
qtrade protocol create `
  --id quality_value_v1 `
  --title "质量价值策略 v1" `
  --hypothesis "高质量且估值合理的公司在日线周期具有稳定超额收益" `
  --development-start 2015-01-01 `
  --development-end 2020-12-31 `
  --validation-start 2021-01-01 `
  --validation-end 2022-12-31 `
  --holdout-start 2023-01-01 `
  --holdout-end 2024-12-31 `
  --signal-frequency month_end `
  --allowed-trials 3
```

草稿保存在：

```text
runtime/research/protocols/quality_value_v1/protocol.yaml
```

冻结前可以审阅草稿。策略逻辑、配置或代码调整完成后，应先提交 Git。

### 15.2 冻结协议

提交并保持研究代码、配置干净后，按照协议中预先声明的频率重建历史信号：

```powershell
qtrade research build-signals `
  --protocol quality_value_v1 `
  --partition development `
  --frequency month_end

qtrade research build-signals `
  --protocol quality_value_v1 `
  --partition validation `
  --frequency month_end

qtrade research build-signals `
  --protocol quality_value_v1 `
  --partition holdout `
  --frequency month_end
```

批量生成器只计算当日排名，不计算或展示未来收益；遇到缺失时点数据会在第一个失败日期停止。
月末或周末频率必须与创建协议时声明的 `signal_frequency` 完全一致。

随后为每个历史分区钉住输入数据和信号版本。该命令只计算输入哈希，
不会运行组合回测，也不会展示封存集收益：

```powershell
qtrade protocol pin-data --id quality_value_v1 --partition development
qtrade protocol pin-data --id quality_value_v1 --partition validation
qtrade protocol pin-data --id quality_value_v1 --partition holdout
```

只有全部排名都具备不可变清单和完整 `available_from` 血缘时才能钉住版本。
验证集和封存集没有固定数据版本时，正式回测会拒绝运行。

随后冻结：

```powershell
qtrade protocol freeze --id quality_value_v1
```

冻结操作会重新记录最近一次影响因子、研究、回测、数据模型或配置的 Git 提交和配置哈希。
这些研究相关路径存在未提交修改时，系统会拒绝冻结；只修改本地操作界面的展示代码不会
使已经冻结的策略失效。

如已经由外部流程计算数据版本，也可以显式指定：

```powershell
qtrade protocol pin-data `
  --id quality_value_v1 `
  --partition validation `
  --version <数据版本哈希>
```

冻结后不要编辑 `protocol.yaml`。任何修改都会造成哈希不匹配，应创建新的协议版本。

### 15.7 当前限制

整理层已经为主要数据集统一生成 `available_from`。财务数据保守设为公告后下一日可用，
因子排名保存所有输入中最晚的可用日期。正式回测遇到缺少 `available_from` 的旧排名会直接失败；
探索性回测仍可运行，但报告会给出血缘不完整警告。

历史股票池现已按上市日、退市日、有效证券简称，以及沪深 300、中证 500

不再把证券主表的当前行业直接回填到过去。

### 15.8 不可变信号版本

因子信号现按内容生成 64 位 SHA-256 `signal_id`，保存到：

```text
reports/factors/<signal_date>/versions/<signal_id>/
```

每个版本包含报告、完整排名和 `manifest.json`。清单记录：

- `signal_id`。
- 信号日期。
- `live_observed` 或 `reconstructed` 来源。
- 分析内容哈希。
- 每个文件的 SHA-256。

相同输入重复生成会复用原版本；结果发生变化会创建新版本，不会覆盖旧版本。
`latest.json` 仅作为界面兼容指针。正式回测直接解析指针、校验版本文件哈希，并记录使用的
每个 `signal_id`；裸的旧版 `rankings.parquet` 只能用于探索性回测。

草稿协议通过 `protocol pin-data` 保存每个分区允许使用的信号 ID 集合和行情输入摘要哈希。
正式验证若发现 `latest.json` 被切换、行情数据被改写或任何输入发生变化，会因数据版本不一致而失败。

批量历史信号命令从交易日历中选择协议声明的月末或周末最后一个开市日。每个信号版本
同时记录协议 ID、Git 提交和配置哈希；代码或配置与草稿协议不一致时拒绝生成。
